## 2. 主题设计

巴法云主题规则（关键，决定消息是否推送）：

| 发布到 | 行为 |
|---|---|
| `<topic>` | 正常推送，所有订阅者收到 |
| `<topic>/set` | 推送给所有订阅者，**发布者自己收不到**（防自循环） |
| `<topic>/up` | **只更新云端数据，不推送**（省流量，适合高频上报） |

本项目主题：

| 用途 | 主题 | 说明 |
|---|---|---|
| 上报生态状态 | `sensor` | 10s 周期，鱼缸六项数据（水温/pH/浊度/TDS/气温/湿度/光照）|
| 上报告警 | `alert` | 异常即时推送 |
| 上报 AI 建议 | `ai` | 小智养护建议（**功能未做**，`bafa_mqtt_post_ai()` 暂无调用者）|
| 设备在线状态 | `status` | 上线通告 `{"state":"online"}`；离线由 **LWT 遗嘱**发 `{"state":"offline"}` |
| 订阅控制命令 | `set` | 手机下行，`esp_mqtt_client_subscribe` |

> ⚠️ **这些主题名必须先在巴法云控制台创建**，否则发布无效。
>
> ⚠️⚠️ 而且**发布失败不会报错** —— 串口照样打「已发布」，云端却是空的。
> 换主题名时务必对着控制台**逐字**核对。

> **2026-10-14 修订**：此前这里是四个各自独立的基名
> （`fishsensor`/`fishalert`/`fishai`/`fishstatus`）+ `fishcmd`，由
> `build_topic()` 往后面拼 `/up` 或 `/set`。但那五个名字**控制台里并不存在**
> （实际建的是 `sensor`/`alert`/`ai`/`status`/`set`），于是所有发布都落到了空处，
> 而串口上完全看不出问题 —— 远端只能看到"消息: 空"。
>
> 现在**主题名即所用**，不再拼后缀（`k_use_set_suffix[]` 与那套拼接逻辑已删）。
> 若想省流量，可把 `BAFA_TOPIC_SENSOR` 直接写成 `"sensor/up"` ——
> 巴法云的 `/up` 语义是"只更新云端数据、不推送"，正适合 10 秒一次的高频上报；
> 但要先确认控制台能显示 `/up` 写进去的数据。

## 3. 上报数据格式

### 3.1 生态状态（`sensor`）

```json
{"ts":12345,"water":{"ph":7.10,"tds":320.0,"ntu":12.50,"wt":25.30},"env":{"at":26.10,"hm":58.0,"lx":450.0}}
```

由 `bafa_mqtt_post_status()` 生成，**113 字节**（各量取满量程的最坏情况）。

> ⚠️⚠️ **消息长度是硬的，而且超限是静默的**
>
> 巴法云官方文档没写单条消息的长度上限。社区反馈是 256 字节，但本工程**实测对不上**：
>
> | 消息 | 长度 | 控制台 |
> |---|---|---|
> | `{"state":"online"}` | 18 字节 | **显示** |
> | 压缩前的状态 JSON | 209 字节 | **永远空白**（旧主题连发两天，一条没留下）|
> | 从控制台手发一条约 200 字符的消息 | ~200 | 提示"发送成功"，卡片**不显示** |
>
> 阈值落在 18~209 之间，**128 是最可能的取值**。故定义 `BAFA_PAYLOAD_SAFE_MAX = 128`，
> 由 `bafa_mqtt_post_status()` 里的守卫盯着，加了字段导致超限会打 `ESP_LOGE`。
>
> **超限的故障方式是最难查的一种**：`esp_mqtt_client_publish` 返回成功、
> 串口打「已发布 → sensor : {...}」、云端一片空白。设备这边看不出任何异常，
> 只有人去控制台看一眼才会发现 —— 而那往往已经是几天后。
> **往这条消息里加字段之前，先算长度。**

**与 `Agent.md` 第 9 节格式的两处偏离**（都是为了塞进长度上限）：

1. **键名缩短**：`turbidity→ntu`、`temp→wt`、`air_temp→at`、`hum→hm`、`lux→lx`。
   `water`/`env` 两层分组保留，只动叶子名。
2. **去掉 `vision` 与 `status` 两段**：
   · `vision` 的 `fish_count`/`muddy` 本来就是**永远为 0/false 的假数据**
     （P6-a 的识别结果只上了屏，从没回写 `s_eco`），报上去等于让云端显示
     "缸里 0 条鱼"这种笃定的假话；
   · `status` 的 `wifi`/`mqtt` 在"能收到这条消息"这个前提下是冗余的，
     而 `alert` 有自己的 `alert` 主题。

### 3.2 告警（`alert`）

```json
{ "alert": "水温 31.2℃ 超过上限 28℃" }
```

### 3.3 AI 建议（`ai`）

```json
{ "ai": "水质正常，建议 3 天后换水 1/4。" }
```

## 4. 下行命令（`set`）

当前已实现的命令解析（`handle_command()`）：

| 命令 | 行为 |
|---|---|
| `on` | 记录日志（P4/P2 阶段挂接灯光/继电器） |
| `off` | 记录日志 |

其它内容按未知命令记录。**解析结果应经事件总线投递**，不要在 MQTT
事件回调里直接操作外设——回调运行在 MQTT 客户端任务上下文。

## 5. 断线重连策略（重要设计决策）

**已显式关闭 ESP-IDF 内建自动重连**（`network.disable_auto_reconnect = true`），
改由本模块的 `esp_timer` 指数退避定时器接管：

```
首次 1s → 2s → 4s → 8s → 16s → 上限 30s 封顶
连接成功即重置回 1s
```

理由：内建 `reconnect_timeout_ms` 只在**初始连接**阶段有效，断线后的重连
间隔不可控（实测会漂移到数分钟），无法满足验收指标「MQTT 断线后 30s 内重连」。

Wi-Fi 侧同理（`components/net_service/wifi_sta.c`），退避参数
`APP_WIFI_BACKOFF_MIN_MS`=1s / `APP_WIFI_BACKOFF_MAX_MS`=30s。

## 6. 线程边界

**所有 `esp_mqtt_client_publish()` 只能出现在 `mqtt_task` 内**，经
`bafa_mqtt_pump()` 从发送队列取消息后发布。其它任务要上报数据，调用：

```c
bafa_mqtt_post_status(&snapshot);   // 生态状态
bafa_mqtt_post_alert("...");        // 告警
bafa_mqtt_post_ai("...");           // AI 建议
```

队列深度 `BAFA_TX_QUEUE_LEN`=8。**队列满时丢弃并告警，不阻塞调用者**——
调用者可能是高优先级 sensor_task，阻塞它会造成整机节拍失真。
