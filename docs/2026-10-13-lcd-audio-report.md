## 2. LCD 背光：`LCD_BL_INVERT` 0 → 1

### 改动

`components/lcd_display/lcd_display.c`

```c
#define LCD_BL_INVERT  1      // 原为 0
```

效果：`lcd_backlight(true)` 从「duty=0 → IO42 拉**低**」变为「duty=1023 → IO42 拉**高**」。

### 为什么

参考工程 06 BSP 在同一块板上**能正常出图**，它点屏的最后一步是：

```c
esp_err_t bsp_lcd_init(void) {
    ...
    ret = bsp_display_backlight_on();   // → brightness_set(100) → duty=1023
}                                       //   且 output_invert = false ⇒ 引脚恒**高**
```

而本项目写的是 `duty=0`（引脚恒低）。两者**正好相反**，只能实测裁决。

### 结果

改完立刻点亮。**「IO42 低电平点亮」的早期实测记录作废。**

> 教训：`pinmap.md` 8.1 曾把「IO42 拉高熄屏、拉低亮屏」记为「已裁决」，
> 并据此把 xiaozhi 的背光配置判定为「可能一直处于熄灭状态」。
> 那套推理的前提是错的。**本项目自己的实测记录也会错**，不只是厂家注释会错。

## 3. LCD 颜色：面板的字段顺序是 R, B, G

### 3.1 排查过程（四轮实测）

| 轮次 | 配置 | 观察结果 |
|---|---|---|
| 1 | `rgb_ele_order = BGR`（MADCTL bit3=1） | 彩条 `蓝｜绿｜红｜白｜黑` |
| 2 | `rgb_ele_order = RGB`（bit3=0） | 彩条 `红｜蓝｜绿｜白｜黑` |
| 3 | 2×5 矩阵（同一固件内枚举 bit3×五色） | 见下表 |
| 4 | 单位位探针（单个 bit 置位，全屏） | 见下 |

矩阵结果：

| 写入 | bit3 = 0 | bit3 = 1 |
|---|---|---|
| `0xF800`（F0 置位） | 红 | 蓝 |
| `0x07E0`（F1 置位） | **蓝** | **红** |
| `0x001F`（F2 置位） | **绿** | **绿** |
| `0xFFFF` | 白 | 白 |
| `0x0000` | 黑 | 黑 |

（F0=`[15:11]`，F1=`[10:5]`，F2=`[4:0]`）

单位位探针（bit3=0）：`0x0020`(bit5)→**蓝**，`0x0040`(bit6)→蓝，`0x0001`(bit0)→绿，`0x0800`(bit11)→红。

### 3.2 推出的结论

**bit3 的行为是标准的**：它交换 F0 与 F1 的去向，在屏幕上表现为红↔蓝互换。

**异常在于 F1 的归属**：标准 RGB565 里 F1（6 位）是**绿**，但这颗面板把它给了**蓝**。
判据是 `0x0020`（bit5）显示**蓝** —— 这一条直接排除了「蓝色只有 5 位、绿占 `[5:0]`」的替代模型。

因此面板实际认的字段顺序是：

```
F0 [15:11] (5 位) → 红
F1 [10:5]  (6 位) → 蓝
F2 [4:0]   (5 位) → 绿
```

### 3.3 代码无法修，只能重排字段

**MADCTL 里没有任何一位能修它**：bit3 只交换 F0/F1 去向，管不到「6 位字段归绿还是归蓝」。
所以必须在送数据前重排字段。

`components/lcd_display/lcd_display.c` 新增：

```c
static inline uint16_t panel_encode(uint16_t rgb565)
{
    const uint16_t r = (rgb565 >> 11) & 0x1F;
    const uint16_t g = (rgb565 >>  5) & 0x3F;
    const uint16_t b =  rgb565        & 0x1F;
    return (uint16_t)((r << 11) | (b << 6) | (g >> 1));
}
```

**为什么 `b << 6` 而不是 `b << 5`**：蓝色是 6 位通道，5 位的 `b` 必须**高位对齐**
才占满量程；低位对齐的话蓝最多只有一半亮度。
代价是绿色丢 1 位精度（6 位数据塞进 5 位字段）—— 这是这颗面板的硬限制。

**接入位置**：全部三条绘制路径（`lcd_fill` / `draw_pattern` / `lcd_draw_progress_bar`）。
调用方仍传标准 RGB565，转换在写入行缓冲那一刻发生 —— **将来接入 LVGL 不需要关心这件事**。

### 3.4 验证

八色全屏探针（红/绿/蓝/黄/青/品红/白/黑）逐一核对，**全部正确**（用户实测确认）。

### 3.5 一处存疑数据

单位位探针中 `0x0010`(bit4) 报的是**蓝**，按上述模型应为绿 —— 4 个点位中错 1 个。
疑为读数时串步（该步前后两次都是蓝）。

**不影响本公式**：`panel_encode()` 已对八个标准色逐一验算并通过实测。

## 4. 音频无声：I2S 引脚抄错（C1 根本不存在）

### 4.1 现象

LCD 正常出图后，音频软件链路**全绿**但**完全无声**。日志证据：

```
audio: I2S 双工通道就绪: MCLK=IO38 BCLK=IO39 WS=IO40 DIN=IO12 DOUT=IO45 @24000Hz
audio:   [步骤1] esp_codec_dev_open(ES8311) -> 0 OK
audio:   [步骤2] 设置音量 70 -> 0 OK
audio:   [步骤4] PCA9557 P1 功放使能 -> ESP_OK
audio: 测试音播放完成
```

**没有任何报错**。这说明不是 API 调用失败，而是**信号没到喇叭**。

### 4.2 真因

I2S 被指到了 **IO39（BCLK）/ IO40（WS）** —— 那正是 **LCD 的 DC / MOSI**。
编解码器收不到位时钟与帧同步，自然无声。

两套厂家已验证代码**完全一致**，都写 BCLK=IO14 / WS=IO13：

| 信号 | [06BSP] `esp32_s3_gec.h:198-202` | [小智] `gec-esp32s3-board/config.h:21-25` | 本项目（错） |
|---|---|---|---|
| MCLK | `GPIO_NUM_38` | `GPIO_NUM_38` | IO38 ✓ |
| **BCLK** | **`GPIO_NUM_14`** | **`GPIO_NUM_14`** | ~~IO39~~ ✗ |
| **WS** | **`GPIO_NUM_13`** | **`GPIO_NUM_13`** | ~~IO40~~ ✗ |
| DOUT | `GPIO_NUM_45` | `GPIO_NUM_45` | IO45 ✓ |
| DIN | `-1`（录音未启用） | `GPIO_NUM_12` | IO12 ✓ |

### 4.3 修复

`components/board_gec/include/gec_board.h`

```c
#define GEC_I2S_BCLK_GPIO   GPIO_NUM_14    /* 曾误写 IO39 = LCD DC   */
#define GEC_I2S_WS_GPIO     GPIO_NUM_13    /* 曾误写 IO40 = LCD MOSI */
```

改完喇叭即正常放声。

### 4.4 被推翻的 C1

`pinmap.md` 把 **C1（LCD 与 I2S 争用 IO39/IO40）** 记为
**「已确认真实冲突，不可回避」「本项目最大架构风险」**，并写进了硬性约束：

> 7.3 约束 3：**IO39 / IO40 冲突未解决前，LCD 与音频功能不得同时初始化。**

**C1 从未存在。** 它是引脚表转抄时把 LCD 的 DC/MOSI 误当成 I2S 的 BCLK/WS 造成的。

### 4.5 一个值得记住的细节

`pinmap.md` 第 4 节**自己引用了** 06 BSP 的
`I2S_BCK_IO=IO14 / I2S_WS_IO=IO13`，却判断其
「与其自身 LCD 配置也不自洽」而**否掉了正确答案**，转而采用 IO39/IO40。

**正确答案当时就在文档里，被推理否决了。**

### 4.6 关于「v0.13 音频验证通过」

那条旧结论**不是假的，但前提有问题**：Agent.md v0.16 记着当时
`spi_bus_initialize` 返回 `INVALID_STATE`、SPI 根本没生效。
IO39/IO40 当时是空的，I2S 才碰巧能用。

所以这不是「回归」，而是**一直错的引脚表被正确工作的 LCD 照出来了**。

## 8. 本次排查的方法论教训

### 8.1 观测与理论冲突时，先把观测做扎实

颜色排查中曾出现两次**互相矛盾**的观测（bit3=1 时 `0x07E0` 显示绿、
bit3=0 时同一值显示蓝）。而 IDF 对 bit3 的定义 `LCD_CMD_BGR_BIT (1<<3)`
只交换红与蓝，`0x07E0` 的置位全在绿色字段内，**理论上不该变**。

正确做法不是挑一个信，而是**把矛盾本身设计成实验**：
在同一份固件内枚举 bit3 两种取值 × 五种全屏单色，得到完整矩阵。

### 8.2 判据要尽量去掉「人为读数顺序」

彩条报告依赖「左→右」这一人为顺序，**报错一位就会把结论带偏**。
改用全屏单色后（一次只出一种颜色），读数歧义即消失。

本项目的替代方案是：**用颜色差异而非亮度差异做判据** ——
在「亮度/极性」这类主观判据上，本项目已经翻过好几次车。

### 8.3 引脚表抄错一位，之后所有推理都在错前提上层层加固

C1 的教训：一个转抄错误，被后续文档反复引用、层层推理，
最后变成「本项目最大架构风险」和「硬性约束」。

**凡有源码可查的取值，一律回源码核对，不转抄二手表格。**
正确答案（`I2S_BCK_IO=IO14 / I2S_WS_IO=IO13`）当时就写在 `pinmap.md` 自己引用的段落里。

### 8.4 本次新添的一条：自己的实测记录也会错

背光极性那条被记为「已实测确认（低电平点亮）」，实际是高电平点亮。
**不要把任何未在当次对照实验中复现过的结论当作前提。**

## 附：构建环境注意事项

从 **Git Bash / MSYS** 环境调用 `build.ps1` 会失败：

```
ERROR: MSys/Mingw is not supported.
```

根因是 ESP-IDF 的 `tools/idf_tools.py` 在 `MSYSTEM` 环境变量存在时直接 `fatal()`，
而 Git Bash 的 `powershell.exe` 包装脚本会重新注入 `MSYSTEM`（用 `env -u MSYSTEM`
也去不掉）。**在 VS Code 的 PowerShell 终端里直接跑 `.\build.ps1` 不受影响。**

若需在 MSYS 下调用，须在 PowerShell 进程内先移除再激活：

```powershell
Remove-Item Env:MSYSTEM -ErrorAction SilentlyContinue
Remove-Item Env:MSYSCON -ErrorAction SilentlyContinue
```
