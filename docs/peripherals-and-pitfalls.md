### 1.2 板载但本项目**不用**

| 器件 | 事实 | 为什么不用 |
|---|---|---|
| **QMI8658A** 六轴姿态传感器 @0x6A | I2C 上确实在应答（每次扫描都能看到） | 本工程用不上；但**它的存在会占 I2C 扫描结果的一行**，别当成异常 |
| 板载 LED | 实测挂在 **IO10**，且与显示信号同脚 | 拉低 IO10 时 **LED 亮 + 屏幕闪** ⇒ 不能当普通 GPIO 用，本项目放弃使用。见 [`pinmap.md` 8.2](pinmap.md) |
| 按键 IO0（BOOT）/ IO11 | 两套厂家资料一致支持 IO0；IO11 为 06 BSP 独有 | 当前交互全在触摸屏，未接按键 |
| USB-Serial-JTAG | 与 CH340K 是**两个串口、同一份日志** | 只作次控制台；设备会在两者之间重新枚举 |

## 二、Flash 分区表

真源：[`partitions.csv`](../partitions.csv)。16MB Flash，`CONFIG_PARTITION_TABLE_OFFSET=0x8000`。

| 分区 | 类型 | 偏移 | 大小 | 作用 |
|---|---|---|---|---|
| `bootloader` | — | `0x0` | 22272 B | 二级引导（启动日志里那几行分区列表就是它打的） |
| `partition_table` | — | `0x8000` | 3072 B | 本表本身 |
| `nvs` | data/nvs | `0x9000` | **64KB** | Wi-Fi PHY 校准数据、巴法云/小智凭据。**从默认 16KB 扩容**：`CONFIG_ESP_WIFI_NVS_ENABLED=y` 会往里写校准数据，16KB 偏紧 |
| `otadata` | data/ota | `0x19000` | 8KB | 双 OTA 槽的选择标志 |
| `phy_init` | data/phy | `0x1B000` | 4KB | RF 校准数据 |
| `model` | data/spiffs | `0x1C000` | **912KB** | **空占位，当前没用**。2026-10-13 为唤醒词预留，最终没引入 esp-sr。留着不花代价：这块空隙本来就夹在 `phy_init` 与 `ota_0` 之间，删掉也不会让 `ota_0` 变大。日后真上 esp-sr，其 CMakeLists 会读本分区自动把 `srmodels.bin` 挂到 `idf.py flash` 上 |
| `ota_0` | app | `0x100000` | **6MB** | 当前运行的固件（app 槽 6MB，当前占 63% —— `partitions.csv` 里记的 62% 是更早一次构建的读数） |
| `ota_1` | app | `0x700000` | **6MB** | 第二个 OTA 槽，保留给后续 OTA 升级 |
| `fonts` | data/spiffs | `0xD00000` | **2MB** | 中文字体 fallback 二进制（`font_noto_qwen_16_4.bin`，1.87MiB）。16MB 尾部空隙，**不挪动任何已有分区** |

**分区表的三条设计约束**（都在 `partitions.csv` 顶部有记录）：

1. 全部 **4KB 对齐、首尾相接、无重叠**；
2. `model` 的 912KB 是「**不挪动其它分区**的前提下能给出的全部空隙」；
3. `fonts` 追加在两个 OTA 槽**之后**，所以加它是零风险的。

**`idf.py flash` 实际写 5 个镜像**（真源：`build/flasher_args.json`）：

| 偏移 | 镜像 | 大小 |
|---|---|---|
| `0x0` | `bootloader/bootloader.bin` | 22272 B = 0x5700 |
| `0x8000` | `partition_table/partition-table.bin` | 3072 B |
| `0x19000` | `ota_data_initial.bin`（otadata） | 8192 B |
| `0x100000` | `smart_fish_tank.bin`（app → `ota_0`） | 3983840 B（槽占用 63%） |
| `0xD00000` | `../fonts/font_noto_qwen_16_4.bin` | 1.87 MiB |

⚠️ **`phy_init` 不在其中**：只有开了 `CONFIG_ESP_PHY_INIT_DATA_IN_PARTITION` 才会单独烧它，
本工程是 `is not set`（校准数据随 app 走）。

最后一行由 [`font_service/CMakeLists.txt`](../components/font_service/CMakeLists.txt) 的
`esptool_py_flash_to_partition()` 自动挂上，**不需要手工 esptool 命令**。
只更新应用：`.\build.ps1 -p COM10 app-flash` —— ⚠️ **它不写字体分区**。

## 三、RTOS：任务、核心与同步

### 3.1 任务表（真源 [`app_config.h`](../main/app_config.h) + [`ui_lvgl_config.h`](../components/ui_lvgl/include/ui_lvgl_config.h)）

| 任务 | 优先级 | 栈(字节) | 核 | 节拍 | 职责 |
|---|---:|---:|---|---|---|
| `sensor_task` | 5 | 4096 | 1 | 1s | 采样 + 阈值判定（当前是随机游走） |
| `voice_task` | 4 | **26624** | 0 | 10ms 空转 / 60ms 帧 | 麦克风 → Opus 编码 → 上行；兼**下行包的唯一消费者** |
| `mqtt_task` | 3 | 6144 | 0 | 阻塞 500ms + 10s 上报 | **唯一允许调 `esp_mqtt_client_publish` 的地方** |
| `play_task` | 3 | 4096 | 0 | 环形缓冲驱动 | 从环形缓冲取 PCM → `esp_codec_dev_write` |
| `xz_client` | 3 | 6144 | 0 | 事件驱动 | 小智 OTA / WSS / 重连。⚠️ **不发应用层心跳**（见 4.9 节） |
| `xz_tool` | 3 | 8192 | 0 | 队列驱动 | **慢工具**（拍照 + JPEG + 上传） |
| `ui_task` | 2 | 6144 | 1 | 30ms（`vTaskDelayUntil`）/ 200ms 出数据 | 读快照 → 上锁更新 LVGL 控件 |
| `taskLVGL` | 2 | 7168 | 1 | 33ms | LVGL 渲染循环（esp_lvgl_port 创建并持有递归锁） |
| `monitor_task` | 1 | 4096 | 1 | 10s | 内存、栈高水位、任务健康 |

> **大部分栈是实测水位收下来的**，不是拍脑袋：接入小智客户端后回头核水位，
> 发现普遍开大了一倍（`ui_task`/`mqtt_task` 实际只用 2.8KB），据此下调仍留 2 倍余量。
> 但**有三个不是实测值**，别把它们当已验证的看：
>
> | 任务 | 栈的来源 |
> |---|---|
> | `voice_task` | 首版 8192 **按下语音键的瞬间就爆栈**，栈被吃在 `opus_encode()` 的 SILK/CELT 调用链上；照参考实现取 **26624** |
> | `xz_tool` | **照 xiaozhi 的初值 8192**，尚未按实测收（见第七节开放事项） |
> | `taskLVGL` | esp_lvgl_port 的**端口默认值 7168**，尚未核对 |

### 3.2 时基（一个会咬人的常量）

`CONFIG_FREERTOS_HZ = 100` ⇒ **1 tick = 10ms**（不是默认的 1000Hz）。

- `pdMS_TO_TICKS(5)` 得到 **0**；
- 所有周期常量必须是 **10 的整数倍**；
- `APP_UI_REFRESH_PERIOD_MS = 30` 不是 10 的倍数 ⇒ `ui_task` 必须用
  `vTaskDelayUntil` 按绝对节拍推进，否则误差累积。

### 3.3 同步机制

| 机制 | 用途 |
|---|---|
| `app_events` 事件总线 | 传感器/视觉/语音/网络 → UI/MQTT/AI 的跨任务投递（队列满时告警，**绝不静默丢弃**） |
| `s_eco_mutex` | 全局生态状态读写（唯一写者规则见下） |
| LVGL 递归锁 | 由 esp_lvgl_port 提供，经 `ui_lvgl_lock/unlock` 暴露给所有更新方 |
| `s_play_lock` + 环形缓冲 | 下行 PCM 的跨任务转运（丢**最旧**，保证延迟有界） |
| `s_dl_q`（PSRAM 静态队列） | 下行 Opus 包的转运（丢**最新**，绝不让网络任务阻塞） |
| `i2c_mutex` | PCA9557 影子寄存器；总线并发由 IDF 的 `i2c_master` 自己保证 |

### 3.4 四条硬性线程边界（违反会出最难查的故障）

1. **慢动作绝不持 LVGL 锁** —— 拍照最长阻塞 4 秒、解 6 张缩略图要几百毫秒。
   持锁做会把 `taskLVGL` 一起卡住 ⇒ 表现是"界面死机 + 触摸失灵"。
2. **只有 `mqtt_task` 调 `esp_mqtt_client_publish`**，其它任务走 `bafa_mqtt_enqueue()`。
3. **慢操作绝不放在 WebSocket 回调里** —— 那跑在协议栈自己的任务上、栈很小
   （实测踩过：在里面解码 Opus ⇒ `stack overflow in task websocket_task` ⇒ **整机复位**）。
   回调只入队，交给专用大栈任务。
4. **`alert_mask` 只有一个写者**（阈值计算处）。加新写者前先 `grep` 出所有写点。

## 四、各外设的协议与启动方式

### 4.0 启动顺序全图（[`app_main.c`](../main/app_main.c)）

```
1.  NVS              nvs_flash_init()：失败且是 NO_FREE_PAGES / NEW_VERSION ⇒ 先 erase
2.  事件总线         必须在任何任务与外设服务之前（否则任务一起来就发布会失败）
3.  全局状态         eco_init()：建互斥锁 + 初值取游走量程中点
4.  网络事件订阅     on_wifi_event / on_mqtt_event → eco_refresh_links()
5.  板级 I2C         gec_board_i2c_init()（挂 PCA9557）—— **下面所有 I2C 器件的前置**
6.  自检             gec_i2c_scan() + 关键器件存在性；**失败不阻止任务启动**（为了串口诊断）
6.5 LCD              p05_run() → lcd_init() + 拉低片选 + 点亮背光
6.6 摄像头           camera_service_init()        ← 失败不致命
6.7 音频             audio_service_init() + enable_output(true) ← 失败不致命
6.8 TF 卡            sd_service_init() + 逐字节自检 + 缩略图自检 ← 失败不致命
7.  网络             wifi_sta_start() → net_time_sync_start()（非阻塞）→ bafa_mqtt_start()
8.  建任务           ui_task / mqtt_task / sensor_task
8.4 Opus + 播放链路  环形缓冲 + s_dl_q + play_task + voice_task ← 必须在 xz_client_start 之前
8.5 小智客户端       先注册回调与两个 MCP 数据源，**再** xz_client_start()
最后 monitor_task（放在最后才能监控到全部任务）
```

**这个顺序不是随意的，三处有硬依赖**：

- 第 5 步必须在**所有 I2C 器件**之前 —— LCD 片选（PCA9557）在 6.5、摄像头 SCCB 在 6.6、
  codec 在 6.7；**触摸更晚**，它在 `ui_lvgl_init()` 里才初始化
  （`ui_lvgl.c`，此时 ui_task 已经跑起来了）。它们全挂在同一条 I2C 上；
- 8.4 必须在 8.5 之前 —— 客户端一连上就可能收下行音频，环形缓冲与 `play_task` 得先就位，
  否则第一批音频会被静默丢弃；
- 8.5 的回调与数据源注册必须在 `xz_client_start()` **之前** ——
  服务器在 hello 之后**立刻**就会发工具请求，注册晚了那一次只能回"取不到数据"。

**"失败不致命"是一条刻意的设计原则**：摄像头、音频、TF 卡、小智客户端任何一项初始化
失败，界面、传感器、巴法云都照常跑，界面上给出中文原因。自检失败也不阻止任务启动。

### 4.1 I2C 总线（一切的地基）

| 项 | 值 |
|---|---|
| 引脚 | SDA=IO1、SCL=IO2 |
| 速率 | **100kHz**（已验证值，不是"能跑更快就更快"） |
| 端口 | `GEC_I2C_PORT_NUM = I2C_NUM_0`，**显式指定** |
| 驱动 | ESP-IDF **新** `i2c_master` 驱动（7 位地址） |

**端口号为什么必须写死**：`esp32-camera` 的 `sccb_i2c_port` 要的正是**端口号** ——
它拿这个号去 `i2c_master_get_bus_handle()` 找**同一条**总线，再只 `add_device` 挂自己的
从设备，**绝不重建总线**。早先写 `-1`（自动分配）时的注释理由「写死端口号会与其它
I2C 使用者冲突」**正好说反了**：写死端口号恰恰是 SCCB 能共享本总线的前提。

**启动**：`gec_board_i2c_init()`（幂等，内部有互斥）。返回句柄供各组件
`i2c_master_bus_add_device()` 挂自己的从设备。

**⚠️ `esp_codec_dev` 的地址陷阱**：它会对传入地址做 `>>1`。若把 ADS1115 的 0x48 交给它，
实际会变成 0x24。**ADS1115 必须用 `i2c_master_bus_add_device(0x48)` 直接挂载。**

### 4.2 PCA9557 —— 板级关键，三个功能都靠它

**协议**：I2C @0x19，寄存器 输入`0x00` / 输出`0x01` / 极性`0x02` / 方向`0x03`（1=输入）。

| 脚 | 位 | 功能 | 有效电平 | 初值 |
|---|---|---|---|---|
| P0 | bit0 | **LCD 片选 CS** | 低有效 | 1（不选中） |
| P1 | bit1 | **音频功放使能 PA_EN** | 高有效 | 0（关闭） |
| P2 | bit2 | **摄像头电源 DVP_PWDN** | 低有效 | 1（断电） |

**启动**：`gec_board_i2c_init()` 内部初始化（先写输出寄存器、再写方向寄存器 `0xf8` = 仅 P0–P2 输出）。

**为什么它是"关键"**：这三个功能**都不占 ESP32 GPIO**。由此推出两条硬事实：

- **LCD 的 `cs_gpio_num` 必须设 NC** —— CS 走 I2C 扩展芯片，`esp_lcd` 无法代管，
  **必须由应用手动拉低**（`lcd_init()` 里 `esp_lcd_panel_reset()` 之后那一步）；
- 误把扩展器脚号填进 `camera_config_t.pin_pwdn` 会把 **GPIO2（I2C SCL）**配成输出并翻转
  ⇒ **整条 I2C 总线当场死**。摄像头必须 `pin_pwdn = -1; pin_reset = -1`。

### 4.3 LCD —— ST7796 @ SPI3

| 项 | 值 |
|---|---|
| 协议 | SPI3_HOST，**模式 3**，**80MHz** |
| 引脚 | MOSI=IO40、SCLK=IO41、DC=IO39、BL=IO42 |
| CS | **PCA9557 P0**（不在 GPIO 上），`cs_gpio_num = NC` |
| RST | **NC** —— 复位走软件命令 `SWRESET(0x01)` |
| 尺寸 | 480×320，RGB565，16bpp |

**启动**：`lcd_init()`（[`lcd_display.c`](../components/lcd_display/lcd_display.c)），
前置条件是 **`gec_board_i2c_init()`**（片选要经 I2C）。序列：
SPI 总线 → panel IO → ST7796 面板 → `reset()` → **`gec_lcd_cs(0)` 拉低片选** →
`init()`（SLPOUT→MADCTL→COLMOD→14 条厂商表）→ `invert_color(true)` →
`swap_xy(true)` → `mirror(true,true)` → **全屏填白清 GRAM** → `disp_on_off(true)`。

**颜色链路的终值（以代码为准）**：

| 项 | 值 | 出处 |
|---|---|---|
| `rgb_ele_order` | **`LCD_RGB_ELEMENT_ORDER_BGR`** | `lcd_display.c` 的 `panel_config` |
| MADCTL 终值 | **0xE8**（BGR 0x08 由 API 累加，MV\|MX\|MY 再累加） | 驱动累加，**不可手写** |
| 传输前变换 | **逐像素字节交换**（`panel_send()` 就地交换） | 全项目**唯一**写面板的出口 |

> **两条缺一不可**：只有 ①（BGR）⇒ 红蓝互换；只有 ②（字节交换）⇒ 绿字段被打散；
> 都没有 ⇒ 红蓝碰巧看着对、绿全错 —— 本项目长期卡在这个状态里。
> 机制与反推见 [lcd-audio 报告](2026-10-13-lcd-audio-report.md)。

**五条绘制路径共用 `panel_send()` 一个出口**（LVGL flush / `lcd_fill` / 彩条 / 棋盘格 /
进度条）。收口是刻意的：此前各路径各写各的，直接导致"LVGL 画的"与"自检画的"颜色不一致，
排障时无法互相印证。

**⚠️ 绘制缓冲不放 PSRAM**（`LVGL_BUFFER_IN_PSRAM = 0`）：IDF 的 SPI 驱动在源缓冲位于
PSRAM 时，会在**每次事务**于内部 RAM 分配一块**等长**缓冲并 memcpy，而这段代码跑在
SPI 中断路径上。详见第五节坑 ③。

### 4.4 触摸 —— FT6X36

**协议**：I2C @0x38，**纯轮询**（`int_gpio_num = NC`、`rst_gpio_num = NC`，原理图上就没接）。
读一次触摸 = 一次 I2C 事务，由 LVGL 的 indev 按需调用（约 30 次/秒）—— 对 100kHz 共享总线可接受。

**方向参数**：`swap_xy=1 / mirror_x=0 / mirror_y=1`，与 06 BSP 完全一致
（本工程 MADCTL 是 MV|MX|MY，与 06 BSP 的几何一致，故可直接沿用）。

**启动**：`touch_input_init()`（[`touch_input`](../components/touch_input/)），
前置 `gec_board_i2c_init()`。**刻意不依赖 LVGL** —— 它只提供「读一次触摸点」，
由 `ui_lvgl` 接到 indev 上。

### 4.5 音频 —— ES7210（录）+ ES8311（放），I2S0 全双工

| 项 | 值 |
|---|---|
| 协议 | **I2S0 双通道**：TX 走 **std 模式**，RX 走 **TDM 模式**（ES7210 是 4 通道 ADC） |
| 引脚 | MCLK=IO38、**BCLK=IO14**、**WS=IO13**、DIN=IO12、DOUT=IO45 |
| 采样率 | 硬件 24kHz / 16bit / MCLK = 256×fs |
| 对外格式 | 录音 **16kHz 单声道 int16**（组件内做 24k→16k 无状态抽取，比例恰为 3:2） |
| 功放使能 | **PCA9557 P1** |
| 编解码器控制 | I2C @0x18（ES8311）/ @0x41（ES7210） |

**启动**：`audio_service_init()` → **立刻 `audio_service_enable_output(true)` 并保持常开**。

> **为什么通路常开而不是"要放音才开"**：`esp_codec_dev` 的通道启停**不做幂等检查**，
> 而 IDF 的 `i2s_channel_disable()` 在通道未启用时返回 `ESP_ERR_INVALID_STATE` ⇒
> `open → close → open` 必然失败，实测现象是**喇叭只响第一次**。
> 代价是 I2S 与 MCLK 持续运行（约几十 mW）。

**麦克风增益必须显式设**：`esp_codec_dev_set_in_channel_gain(..., CH0, 37.5dB)`。
不设的话表现为"上行发送全成功、服务器一条文本都不回" —— 日志上一切正常。

**上行的两个协议常量**（`audio_service.h` / `opus_codec.h`，与 `xiaozhi_config.h` 一致）：

| 方向 | 格式 |
|---|---|
| 上行 | Opus，**16kHz 单声道 60ms/帧**（960 样本）—— 协议契约，不要改 |
| 下行 | Opus，采样率**以服务器 hello 的 `audio_params` 为准**（通常 24kHz） |
| 二进制帧 | 协议版本 1 = **裸 Opus，无帧头** |

### 4.6 摄像头 —— GC0308（DVP 并口）

| 项 | 值 |
|---|---|
| 协议 | **DVP 并口**（8 位数据 + PCLK/VSYNC/HREF） + **SCCB 配置**（复用 I2C0） |
| 型号 | **GC0308**（PID=0x9B / I2C 0x21）—— 不是 OV2640（那会是 0x30 / PID 0x26） |
| 输出 | QVGA **320×240 RGB565**，`fb_count=1`，帧缓冲在 PSRAM（153600 B） |
| XCLK | 24MHz（**S3 的 XCLK 由 LCD_CAM 产生**，`ledc_channel/timer` 两项不参与） |
| 电源 | **PCA9557 P2**（低=上电），`pin_pwdn = -1; pin_reset = -1` |
| SCCB 端口 | **`I2C_NUM_0`** —— ⚠️ **不能照抄 xiaozhi 的端口 1**，抄错会得到 `failed to get SCCB I2C Bus handle` |

**启动**：`camera_service_init()`，前置 `gec_board_i2c_init()`。
顺序：PCA9557 P2 置 0 上电 → 等 100ms 稳定 → `esp_camera_init()` → 分配输出缓冲。
失败**不致命**，`camera_service_status()` 给出中文原因供界面显示。

**两条最容易搞错的**：

1. **字节序**：DVP 交出的是**大端** RGB565，而 S3 是小端 ⇒ 交给 LVGL 前必须逐像素
   `__builtin_bswap16`。**判据很硬**：照片花屏但**界面正常** ⇒ 就是这一处
   （两者走同一条 `panel_send()` 出口，界面正常说明面板侧没问题）。
   链条上共两次交换，另一次在 `panel_send()`，**各管一段**。
2. **`fb_count=1` 下"丢弃第 1 帧"不是优化，是功能正确性**：上次 `fb_return()` 之后
   驱动会在下一个 VSYNC 立刻预采一帧并排队，那帧会**一直老化到下次拍照** ——
   不丢弃它，用户按下快门拿到的会是**上一次按快门时的画面**。

### 4.7 TF 卡 —— SDMMC 1-bit + FATFS

| 项 | 值 |
|---|---|
| 协议 | **SDMMC 1-bit**（只用 CMD/CLK/DAT0） + **FATFS** |
| 引脚 | **CMD=IO48、CLK=IO47、DAT0=IO21**（来源：主板原理图，标注 "1-SD mode"） |
| 时钟 | 20MHz（`GEC_SD_FREQ_KHZ`） |
| 挂载点 | `/sdcard` |
| card-detect | **没接** ⇒ "卡在不在"只能靠访问发现（`disk_status_check_enable = true`） |

**启动**：`sd_service_init()` → `esp_vfs_fat_sdmmc_mount()`；成功后
`sd_service_selftest()`（写 4KB → 读回 → **逐字节比对**）+ `sd_probe_newest_thumb()`
（列目录 → 读文件 → JPEG 解码 → 校验尺寸）。

**为什么"挂载成功"不算验证过**：DAT0 接触不良可以让卡正常初始化、却在数据阶段丢字节，
而那种故障平时完全看不出来，要等某张照片存坏了才发现。**逐字节比对是唯一能钉死它的判据。**

**四个会炸的坑**（都在 [`sd_service.c`](../components/sd_service/sd_service.c) 的 ⚠️ 里）：

1. **`slot.width` 必须显式设成 1**。`SDMMC_SLOT_CONFIG_DEFAULT()` 给的是 `width = 0`，
   而 0 的含义是"用这个槽的最大宽度"，`soc/esp32s3/sdmmc_periph.c` 两个槽都声明成 `.width = 8`
   ⇒ 驱动会去配 d1..d7，而结构体里那几个字段是全零初始化的 ⇒ **GPIO0..GPIO7**，
   它们**恰好全是合法 GPIO**，`GPIO_NUM_CHECK` 会放行。后果：GPIO0（BOOT 键）、
   IO3/4/5/6/7/8/9（摄像头数据脚与时钟）**被 SD 驱动接管**，画面坏得莫名其妙且看不出跟 SD 有关。
2. **`format_if_mount_failed = false`**：打开它的话，一旦 DAT0 接触不良（卡能初始化、
   FAT 读失败），`s_f_mount()` 会**分区并重新格式化一张完全正常的卡**。失败就失败，让用户自己决定。
3. **`swap_color_bytes = 0`**：esp_jpeg 自己的 example 写的是 1，**不能照抄**。
   判据：缩略图颜色不对但界面正常 ⇒ 就是这里（与摄像头同款判据）。
4. **`esp_jpeg_get_image_info()` 不把 `out_scale` 算进 width/height**，而**同一族的
   `esp_jpeg_decode()` 算**。两个函数语义不一致、头文件又没写，很容易拿 320 去跟 160 比，
   永远不成立 ⇒ **实测代价**：卡里两张 320×240 的照片在相册页全显示不出来，
   而电脑上都能正常打开；串口那句"缩到 1/8 仍超过 160x120"是**假话**。
   现在的做法：只用 `SCALE_0` 取一次**原始尺寸**，缩放比自己算。

### 4.8 中文字体 —— flash 分区 mmap

**协议**：把 `fonts` 分区 mmap 出来，用上游 `cbin_font_create()` 建成 `lv_font_t`，
挂在普惠体后面当 **fallback**。

**启动**：`font_service_init()`（在 `ui_lvgl_init()` **之前**调）。
分区缺失/内容不对时**只打 WARN**，界面照常。

**为什么要它**：`78/xiaozhi-fonts` 的普惠体是**子集化**字体（6649 码位，CJK 仅 **5258**），
按「DeepSeek-R1 ∪ Qwen3 分词器字符」裁剪 —— 而屏幕上的中文大部分来自 AI，**说什么不受控**。
Noto 版覆盖 CJK 10335 个。代价实测 **内部堆 +420 字节**。

**⚠️ ABI 约束**：cbin 里的 `lv_font_fmt_txt_glyph_dsc_t` 是**编译期大小决定**的
（`LV_FONT_FMT_TXT_LARGE`），两边不一致会**渲染出乱码而不是报错**。
`font_service.c` 里有 `_Static_assert` 钉着。

### 4.9 网络链路

| 链路 | 协议 | 端点 / 参数 | 启动 |
|---|---|---|---|
| Wi-Fi | 802.11 STA | — | `wifi_sta_start()`，**非阻塞**、事件驱动、指数退避 1s→30s |
| 对时 | **SNTP** | — | `net_time_sync_start()`，非阻塞、幂等，先等 Wi-Fi 再发请求 |
| 巴法云 | **MQTT 3.1.1 明文 TCP** | `bemfa.com:9501`，**client_id = UID**，user/pass 留空，QoS 0，keepalive 60s | `bafa_mqtt_start()`（建队列 + 起客户端，非阻塞） |
| 小智 OTA | **HTTPS POST** | `https://api.tenclass.net/xiaozhi/ota/` | `xz_client_start()` 内部第一步 |
| 小智对话 | **WSS** + JSON 控制帧 + 二进制 Opus 帧 | 服务器在 OTA 响应里给 url/token | 同上 |
| MCP 工具 | **JSON-RPC**（在 WSS 上） | `initialize` / `tools/list` / `tools/call` | 工具表在连接建立时报给服务器 |
| 视觉上传 | **HTTP(S) POST** | 超时 30s（比 OTA 宽得多） | 在 `xz_tool` 任务上跑 |

**巴法云的三条约定**（详见 [`mqtt_protocol.md`](mqtt_protocol.md)）：

- 主题必须**先在控制台创建**，名字对不上时**发布不报错**；
- 主题：`sensor`（10s 周期）/ `alert`（异常即时）/ `ai`（未做）/ `status`（含 **LWT 遗嘱** `{"state":"offline"}`）/ `set`（下行订阅）；
- **单条消息长度有上限**：实测 18 字节能显示、209 字节一条不显示 ⇒
  取 `BAFA_PAYLOAD_SAFE_MAX = 128`，当前状态 JSON 113 字节。**超限完全静默。**

**重连策略**：**显式关闭** IDF 内建自动重连（`disable_auto_reconnect = true`），
改由本模块的 `esp_timer` 指数退避接管（1→2→4→8→16→上限 30s，连上即重置）。
理由：内建 `reconnect_timeout_ms` 只在**初始连接**阶段有效，断线后的重连间隔不可控
（实测会漂移到数分钟），无法满足"断线后 30s 内重连"。

**小智链路的超时**（逐项照搬 xiaozhi）：HTTP 10s / WS 握手 10s / hello 10s /
视觉 30s / **空闲 120s 判通道超时**（xiaozhi 不发应用层心跳，靠"有没有收到数据"判断）。

**⚠️ TLS 缓冲**：wss 是**常驻**的，mbedtls 默认为每条连接常驻分配
16KB(in) + 4KB(out) = **20KB 内部 RAM**，而这条连接 99% 时间空闲。
`CONFIG_MBEDTLS_DYNAMIC_BUFFER=y` 让它按需分配、用完释放。

### C. 内存与栈

| # | 症状 | 真相 | 判据 / 修法 | 教训 |
|---|---|---|---|---|
| C1 | 打印出 `内部堆: 空闲 8579952 / 总计 373107` —— **空闲是总计的 23 倍** | **堆口径不一致**：`esp_get_free_heap_size()` 返回的是**全部堆**（含 PSRAM），而"总计"用的是 `heap_caps_get_total_size(MALLOC_CAP_INTERNAL)` | 正确配对：内部堆用 `esp_get_free_internal_heap_size()`；PSRAM 用 `heap_caps_get_free_size(MALLOC_CAP_SPIRAM)` | 打印比值时分子分母**必须来自同一口径的 API**。验收判据**必须用内部堆** —— 算上 8MB PSRAM 的全堆余量永远好看（实测 97%），会把内部 RAM 的真实压力完全掩盖 |
| C2 | 栈水位读数看着宽裕 4 倍 | `uxTaskGetStackHighWaterMark()` 在 **ESP-IDF 中返回字节**，不是标准 FreeRTOS 文档所说的"字" | IDF 的 `task.h` 原文：*"in bytes (as opposed to words in the standard FreeRTOS documentation)"* | 核对第三方 API 的单位时**以该 SDK 的头文件注释为准**，不要凭通用文档推断 —— 厂商常改语义。这个错误正好把「栈要爆了」误判成「很安全」 |

| C4 | **按下语音键的瞬间就爆栈**（"开始上行"日志之后即崩） | 栈被吃在 `opus_encode()` 上 —— 它内部的 SILK/CELT 调用链很深。首版只给了 8192 | 照参考实现取 **26624**（那是同一块板上验证过的数字）。⚠️ 注意本工程是 `-Og` 构建，栈帧比优化构建大得多 | 栈大小要么实测、要么照搬**同上下文**已验证的值，"取个中间值"会再爆一次 |
| C5 🔇 | **一说话就整机复位**，连"哪一步崩的"都留不下 | 在 `xz_on_audio` 回调里解码 Opus，而那个回调跑在 **esp_websocket_client 自己的任务**上，栈是组件默认值、不归我们管 | 报错 `stack overflow in task websocket_task`。修法：回调**只入队**，解码交给大栈的 `voice_task` | **回调的栈不归你管。** 慢操作、深调用链一律先入队再挪到自己的任务上 |
| C6 | 内部堆余量掉到 15%，远低于 30% 验收线 | 常驻 wss 的 TLS 缓冲 (**20KB**)、lwip TCP 缓冲、Wi-Fi 缓冲全挤在内部 RAM | 逐项**对比参考工程的 sdkconfig** 找出差距：`MBEDTLS_DYNAMIC_BUFFER`、`SPIRAM_MALLOC_ALWAYSINTERNAL` 16384→512、Wi-Fi 缓冲数、**关掉 Wi-Fi 的 IRAM 优化** | ESP32-S3 的 **IRAM 与 DRAM 共享同一块物理 SRAM** —— 把 Wi-Fi 代码搬进 IRAM 就等于从内部堆里挖走同样多的字节。这类"参考工程开了、我们没开"的配置项**最难凭空想到**，只能靠逐项对比 |
| C7 | 堆余量长期停在 16%，怎么调都上不去 | 栈**普遍开大了一倍**（`ui_task`/`mqtt_task` 实际只用 2.8KB） | 回头核高水位读数后再收，仍留 2 倍余量 | **这是纠正过量分配，不是压缩安全边际。** 但开机水位不等于最坏情况 —— 没跑过活的任务，水位读数是假的 |

### D. 并发与时序

| # | 症状 | 真相 | 判据 / 修法 | 教训 |
|---|---|---|---|---|
| D1 | **告警偶尔闪一下就没了，像是随机的** | `eco_refresh_links()` 里有一句 `s_eco.alert_active = false;`，而它被 `mqtt_task` **每 10 秒**调一次 ⇒ 任何由采样算出的告警**活不过 10 秒** | 删掉该行；`alert_mask`/`alert_active` **只有一个写者**（本条已升格为第 3.4 节第 4 条） | **给共享状态新增写者之前，先 `grep` 出这个状态当前所有的写点。** 那句 `= false` 的注释写着"P1 接入后改写"，读起来像"留给将来的占位"—— 但它**每 10 秒都在执行**。**注释说的是将来，代码做的是现在** |
| D2 | **喇叭只响第一次**：`open → close → open` 循环必然失败 | `esp_codec_dev` 的平台层 `_i2s_drv_enable()` 直接调 IDF 接口而**不做状态检查**，而 `i2s_channel_disable()` 在未启用时返回 `ESP_ERR_INVALID_STATE` | 日志：`i2s_channel_disable: the channel has not been enabled yet` / `i2s_channel_enable: the channel has already enabled`。修法：通路**常开**，静音只切功放使能 | 用第三方库前先读它**怎么调底层 API**。**"接口看起来幂等"不等于"实现是幂等的"** —— 这里成对调 `open()/close()` 的直觉是错的 |
| D3 | 拍照时**界面死机 + 触摸失灵** | 在持 LVGL 锁时调 `esp_camera_fb_get()`（最长等 4 秒），把 `taskLVGL` 一起卡住 | 修法：按钮只置标志 → `ui_task` 在**锁外**轮询 → 抓帧 → 再上锁只切一次指针。照片用**双缓冲**，锁持有时间从"拷 153KB 的几毫秒"降到**微秒级** | **这个次序是设计的一部分，不是优化。** 上板验证时特意测了"拍摄期间界面/触摸是否正常" |
| D4 🔇 | 用户按下快门，拿到的是**上一次按快门时的画面** | `fb_count=1` 下，上次 `fb_return()` 之后驱动会在下一个 VSYNC 立刻预采一帧并排队，那帧**一直老化到下次拍照** | 丢前 N 帧（`CAMERA_SERVICE_WARMUP_FRAMES`）。实测确认：在镜头前挥手，画面实时跟随 | **"丢弃前几帧"不是可选的优化，是功能正确性的一部分** |
| D5 🔇 | TTS 整段整段地丢 | 下行包队列首版只给了 3 格，而服务器下发 TTS 是**成批**的、不是按播放速率匀速吐 | 日志 `下行包队列已满，丢弃（累计 21 个）`。队列加大到 24 格（≈1.4 秒），存储放 PSRAM | **用缓冲解耦"成批的生产者"与"实时的消费者"，而不是指望消费者跑得够快** |
| D6 | 每 10ms 一条 `pump 返回 ESP_ERR_INVALID_STATE` 把日志淹了 | ① `bafa_mqtt_pump()` 在队列未创建时**立刻返回**，没有等待超时 ⇒ `mqtt_task` 全速空转；② 调用方对每个非 OK 都告警，把**正常的状态波动**当成异常 | 修法：① pump 未就绪时也**吃满超时**；② 只对真正的意外告警 + 10 秒节流；③ `app_main` 把服务启动提到任务创建**之前** | **阻塞式 API 的"未就绪"分支必须仍然消费它的超时**，否则调用方会变成忙等循环。**日志要能区分「异常」与「正常波动」** |

### E. 云端与协议

| # | 症状 | 真相 | 判据 / 修法 | 教训 |
|---|---|---|---|---|
| E1 🔇 | 发布返回成功、串口打「已发布」、**云端一片空白** | **主题名对不上**（那五个名字控制台里并不存在）+ **消息超长** | 实测：18 字节能显示、209 字节一条不显示 ⇒ 阈值落在 18~209 之间，取 **128** 做 `BAFA_PAYLOAD_SAFE_MAX`，代码里有守卫 | **超限的故障方式是最难查的一种** —— 设备这边看不出任何异常，只有人去控制台看一眼才会发现，而那往往已经是几天后。**发布失败不报错的通道，必须由代码自己来喊** |
| E2 🔇 | **上行发送全成功，服务器一条文本都不回** | **麦克风增益没显式设**，录音"有波形但极轻"，本地看 RMS 有数、远端 ASR 听不出内容 | 判据：**上行静音帧只有 2~5 字节，带声音是 108~113 字节/帧**。修法：显式 `set_in_channel_gain(..., 37.5dB)` | 给此类链路留一个**能自己报出"带没带声音"的指标**（平均帧长），比事后推理可靠得多 |
| E3 🔇 | AI 答"都正常"，**而当时数据已越界** | MCP 工具描述没写清"每次都要重新调用"，模型拿**上一次调用返回的过期真数字**作答 | 修法：工具描述里显式写 `IMPORTANT: ... never answer from the values of an earlier call` | **从回答上根本看不出错** —— 它报的是真数字，只是过期的。**"过期为真"比"明确错误"更难发现** |
| E4 🔇 | 相册页说"最近 0 张（2 张无法显示）"，而卡里的照片电脑上都能打开 | `esp_jpeg_get_image_info()` **不把 `out_scale` 算进 width/height**，而同一族的 `esp_jpeg_decode()` 算 —— 拿 320 去跟 160 比，永远不成立 | 只用 `SCALE_0` 取一次**原始尺寸**，缩放比自己算。串口上那句"缩到 1/8 仍超过 160x120"是**假话** | **日志说错话比没有日志更费时间。** 返回值必须能区分"解析失败"与"尺寸不合适"，不能把所有情况归到同一句话里 |

| E6 🔇 | 云端那条 `online` 会**永远挂着** | 只在连上那一刻发一次 `online`，没有离线通告 | 加 **LWT 遗嘱**：设备掉线/断电时由服务器代发 `{"state":"offline"}` | **一个永远说"在线"的状态位，比根本没有状态更糟**（周期性心跳仍未做，属已知缺口） |
| E7 🔇 | 「远程查看告警」这件事**从来没成立过** | `bafa_mqtt_post_alert()` 写好了却**一个调用者都没有** —— 告警只喂给了屏幕聊天流 | 接到 `ui_task` 的告警分支上，与屏幕那条并排、同一次触发 | **写好了的函数不等于接上了的链路。** 交付前要问一句"它的调用者是谁" |
| E8 | 开屏那行"鱼缸基本情况汇报"看着像 AI 的开场白 | 它是**本机拼的**，用的却是助手角色；而且读的是**模拟值**、还是**开机那一刻的快照** | 删掉。聊天流从此**只出现真实发生过的事** | ①**把没发生过的话记在 AI 头上，比数据不准更难发现**；②拿模拟值冒充实测不可接受；③开机快照播完就过期，看起来像读数、实际是历史值 |

### G. 方法论（最贵的几条）

这几条不是"某个参数错了"，而是**做事的方式错了**。它们的代价远大于上面任何一条。

| # | 教训 | 说明 |
|---|---|---|
| **G1** | **"参照"已验证代码 ≠ "复用"已验证代码** | LCD 排查耗了十余轮，根因不是某个参数错，而是**方法论错**：自己选 SPI 模式、自己定 `max_transfer_sz`、自己设计绘制缓冲（307KB 整帧→15KB 条带，两次都绕过已验证的"逐行 960 字节"路径）、自己删掉片选步骤、自己造参数扫描框架。**面对"官方/厂家已有可用实现"的场合，复制的成本远低于理解后重写的成本。** 只有当你已经能证明原实现错在哪里时，才谈优化 |
| **G2** | **偏离已验证的参考实现，必须同时写下判据与验证方式** | 本项目颜色排查的最终根因，两条都是**偏离参考且未验证**：两套厂家参考都写 BGR，本项目唯一写成 RGB；xiaozhi 的 `swap_bytes = 1` 被"推理"否定。两次偏离都只在注释里写了句"实测裁决"，而**做出该裁决时测试本身是错的**。**只写"实测"两个字的偏离，一律视同未验证** |
| **G3** | **在证明"测试是对的"之前，它的结果不能用来下结论** | 判定 LCD 颜色时连续踩了三次，每次形态不同、机理相同：① 纯色探针（对结构性错误不敏感）"通过"了但面板是错的；② 在**同时含两个错误**的状态下逐个判定单参数（两个错误互相抵消）；③ `lv_color_hex(0xF800)` 被当成 RGB565（实收 RGB888）。**做法：让测试回读自己的输入** —— 色卡同时回读 LVGL 发出的值与 flush 回调里送去面板的首像素，两条独立证据 + 照片互为交叉验证 |
| **G4** | **判据要尽量去掉「人为读数顺序」** | 彩条依赖"左→右"，**报错一位结论就反**。改用全屏单色、再到**一屏自标注色卡**（一次拍照判完、每格自带文字、不依赖顺序与记忆）之后，读数才可靠。此前多轮互相矛盾的结论，**几乎都源于读数方式本身** |
| **G5** | **观测与理论冲突时，先把观测做扎实，而不是挑一个信** | 颜色排查中出现过两次互相矛盾的观测。正确做法是**把矛盾本身设计成实验**：在同一份固件内枚举 bit3 两种取值 × 五种全屏单色，得到完整矩阵。**优先用颜色差异而非亮度差异做判据** —— 本项目在"亮度/极性"这类主观判据上翻车多次 |
| **G6** | **不要把"某个参考实现应该是好的"当作前提去推结论** | 「C1 是硬件级冲突」那条结论的**前提是"xiaozhi 的 LCD 是工作的"**，而事实是它的屏从来没有过任何显示。**要么实测那个参考实现，要么承认未知。** 本项目在 C1 上有过两次基于未验证前提的结论，均已撤回 |
| **G7** | **绝不写"在失败时也成立"的日志** | 曾经有一条说反了的日志把整个排查方向带偏；也有日志把"缩到 1/8 仍超限"说成结论、而那是句假话。**日志说错话比没有日志更费时间** |
| **G8** | **判错的结论要留在文档里** | 连同它错在哪、被什么判据推翻。`pinmap.md` 的 8.0i 节、`app_config.h` 里那一长串「已裁决完毕、代码已删除的试验（结论保留在此）」，都是这个用途 —— **重复踩同一个坑的代价更大** |
| **G9** | **并行复核换来了一个自己看不见的 bug** | `alert_active` 被周期性清零那条（D1），复核者读的是"**所有**写这个状态的地方"，而设计者盯的是"**自己**要写的地方" —— **视角差异正是复核的价值所在** |
| **G10** | **测试要能自证，判据要能不依赖人** | 麦克风好坏靠"板子自己响/静交替"比 RMS（≈15.8 倍），而不是"人在正确时刻说话" —— **声源是板子自己，结论与用户在不在说话无关**。同理，`sd_service_selftest()` 做**逐字节比对**而不是"挂载成功即通过" |

不转抄二手表格。

**加任何一条绘制路径**：必须经过 `panel_send()`，不要在别处做颜色变换。

**给共享状态加写者之前**：`grep` 出它**当前所有**的写点。

**往巴法云状态 JSON 里加字段之前**：先算长度（上限 128）。

**加任何周期常量**：必须是 **10 的整数倍**。

**动过 CMakeLists / sdkconfig 之后**：看一眼 `build/flasher_args.json` ——
它是"**实际会烧哪些镜像、烧到哪个偏移**"的真源，比读 CMakeLists 推断可靠
（本文第一版就在这里写错过：把不存在的 `phy_init` 算进了烧录清单）。

**调任何栈大小之前**：看 `monitor_task` 的高水位读数，**且那个任务必须已经干过活**
（开机水位不等于最坏情况）。

**加任何 MCP 工具描述**：必须显式写"每次都要重新调用，不要用上一次的结果"。

**结束任何一次排查之前**：确认判据本身站得住（能不能回读自己的输入？有没有人为读数顺序？）。
**症状部分好转 = 底下还有第二个问题。**

**每加一个被监控的任务**：`s_monitored[]` 只有 **8 格**，满了 `monitor_register()` 会
**静默丢弃** —— 加任务必须先扩容 `APP_MAX_MONITORED_TASKS`。
