## 2. 摄像头：从驱动到上屏

### 2.1 组件与配置

走组件管理器拉 `espressif/esp32-camera ~2.1.2`（实解析 2.1.8，自动带 `esp_jpeg`）。

> **关键前提**：xiaozhi 本身就是用 **ESP-IDF v5.5.3** 构建的
> （其 `build/project_description.json` 的 `idf_path` 可证），与本工程同版本。
> 所以这套驱动 API 组合是**在同版本上跑通过的**，不是纸面推断。

Kconfig（`sdkconfig.defaults`）：`CONFIG_GC0308_SUPPORT=y`、
`CONFIG_SCCB_HARDWARE_I2C_DRIVER_NEW=y`、`CONFIG_CAMERA_DMA_BUFFER_SIZE_MAX=8192`
（默认 32768 → 8192，这是摄像头最大的**内部 RAM** 开销；8KB 是 xiaozhi 在同板上的取值）。

### 2.2 ⚠️ sensor 是 GC0308，不是 OV2640

首版上板实测：

```
I camera: Camera PID=0x9b ... Detected GC0308 camera
I camera: Detected camera at address=0x21
I camera: sensor: GC0308 (PID=0x009B)，320x240 RGB565
```

**PID = 0x9B、I2C 地址 0x21**。OV2640 会是 PID 0x26 / 地址 0x30。

此前**所有**文档与注释都按「OV2640 类」描述 —— 这是又一次**没有实测的想当然**
（与"1 比特字段错位""C1 引脚冲突"同源）。已全面更正，见
[pinmap.md 5.2 节](pinmap.md#52--sensor-型号是-gc0308不是-ov2640)。

### 2.3 字节序：链条上两次交换，各管一段

```
GC0308 ──DVP──▶ fb->buf（**大端** RGB565，高字节在前）
                  │  __builtin_bswap16        ← ① camera_service 做
                  ▼
            LVGL 缓冲（标准 native LE RGB565）
                  │  panel_send()             ← ② lcd_display 既有的出口
                  ▼
              ST7796 面板
```

- 驱动侧证据：`cam_hal.c` 初始化时 `swap_data = 0`，`ll_cam.c` 把它直接写进
  `LCD_CAM.cam_ctrl.cam_byte_order` ⇒ 硬件不做交换；`to_jpg.cpp` 也默认按大端解读。
- **判据（很硬）**：照片花屏而**界面正常** ⇒ 就是 ① 漏了。
  因为界面与照片走**同一条** `panel_send()` 出口，界面正常说明面板侧没问题。

### 2.4 并发设计：这个次序是设计的一部分

```
[taskLVGL]  按钮回调 ──只置一个 volatile bool──▶  （回调在 LVGL 锁内，不能做耗时操作）
                                                      │
[ui_task]   每 30ms 锁外轮询 ◀────────────────────────┘
    │  ① ui_lvgl_set_ai_status("拍摄中…")   —— 内部上锁，很快返回
    │  ② camera_service_capture()           —— **锁外**，最长阻塞 4 秒
    ▼  ③ ui_lvgl_show_photo()               —— 内部上锁，只切一次指针
```

**① 拍照绝不能在持 LVGL 锁时做** —— `esp_camera_fb_get()` 最长等 4 秒，
持锁会把 taskLVGL 一起卡住，表现为"界面死机 + 触摸失灵"。

**② 照片用双缓冲**：数据先拷进 ui_lvgl 自有的两块缓冲之一（**锁外**完成），
然后才上锁、只做一次 `lv_image_set_src()` 切换指针。两个好处：
- 锁持有时间从"拷 153 KB 的几毫秒"降到**微秒级**
- LVGL 正在渲染的那块永远不会被下一帧写 ⇒ **撕裂从设计上不可能发生**

> 对照：xiaozhi 的 `Esp32Camera::Capture()` 是**单缓冲、在锁外改写正在显示的缓冲**
> —— 它靠的是"不发生"，不是"不可能"。本项目不学这一处。

**③ `fb_count=1` 下"丢弃第 1 帧"不是优化，是功能正确性**：
上次 `fb_return()` 之后驱动会在下一个 VSYNC 立刻预采一帧并排队，那帧会**一直老化
到下次拍照**。不丢弃它，用户按下快门拿到的会是**上一次按快门时的画面**。
实测确认了这一点（在镜头前挥手，画面实时跟随）。

### 2.5 有意偏离参考实现之处

| 项 | 本项目 | xiaozhi | 理由 |
|---|---|---|---|
| 帧尺寸 | QVGA 320×240 | VGA 640×480 | 屏幕 480×320 ⇒ 1:1 不缩放；内存 1/4；字节交换循环 1/4 |
| SCCB 端口 | `I2C_NUM_0` | 端口 **1** | ⚠️ **不能照抄** —— xiaozhi 的总线在端口 1，本项目在端口 0 |
| 触发 | 界面触摸按钮 | MCP 工具 `self.camera.take_photo`（AI 发起） | 本项目没有 MCP |
| `Explain()` 上传 | **不做** | 上传到它的云服务做 AI 看图 | 本轮需求是"拍照并当场显示"，不含上传 |
| C++ 包装类 | 去掉，纯 C | `Esp32Camera` 类 | 工程其余组件都是 C |

**I2C 端口改动**：`board_gec` 原先用 `.i2c_port = -1`（自动分配），注释理由是
「写死端口号会与同工程内的其它 I2C 使用者（SCCB、触摸屏）冲突」——**这个理由正好说反了**。
`esp_camera` 的 `sccb_i2c_port` 要的正是**端口号**，靠它去 `i2c_master_get_bus_handle()`
找到**同一条**总线再只 `add_device` 挂自己的从设备。写死端口号恰恰是共享总线的前提。
已改为显式 `GEC_I2C_PORT_NUM = I2C_NUM_0`。

上板后 I2C 扫描仍是 5 个器件，无影响。

### 2.6 两个引脚陷阱（都会造成难以定位的故障）

1. **`GEC_PCA9557_IO_DVP_PWDN = 2` 是扩展器脚号，不是 GPIO 号。**
   若误填进 `camera_config_t.pin_pwdn`，驱动会把 **GPIO2（I2C SCL）**配成输出并翻转
   ⇒ **整条 I2C 总线当场死**。必须 `pin_pwdn = -1; pin_reset = -1`，
   电源一律走 PCA9557。
2. **XCLK 是整数分频**（`160MHz / xclk_freq_hz`）：请求 24 MHz 实际约 **26.7 MHz**。
   参考工程同参数可用；若日后出现噪点/丢行，把 `GEC_CAM_XCLK_FREQ_HZ` 试 20 MHz。

## 3. 传感器模拟数据 + 告警链

ADS1115 不购买了，pH / TDS / 浊度等一律由**随机游走**生成。

- 新增 `sensor_task`（优先级 5 / 栈 4096 / core 1 / 周期 `APP_SAMPLE_PERIOD_MS`=1s，
  用的都是 P1 规划里早就预留的参数）
- **游走而非重掷**：真实传感器读数是连续变化的；每次重掷会让数值乱跳、
  告警位每秒翻转，看的人会以为程序坏了
- **量程略超出阈值** ⇒ 告警**偶发**触发（既不永不触发，也不一直红）
- **步长用量程的比例** —— 各量纲差几个数量级（pH 0.1 与光照 100 lx 不是一回事）
- **告警滞回**：越界即进，但要回到阈值内一定幅度才退出。不加滞回的话，
  数值在阈值附近游走会让告警位每秒翻转 ⇒ 卡片颜色闪烁

**告警用位掩码而不是一个 bool**：界面需要知道**是哪一项**超了才能只标红那一张卡。
`tank_ecosystem_t` 新增 `alert_mask`，位定义 `ECO_ALERT_*` 在 `app_core/app_types.h`
（那里也说明了为什么阈值仍在 main 侧 —— 组件不能依赖 main）。

**新增气温/湿度阈值**：鱼缸页有六张卡，而原来只有五组阈值，"气温""湿度"两张卡
永远不可能告警。告警链要么打通到每一张卡，要么就别在界面上留半成品。

### 3.1 修掉一个已埋好的 bug

`eco_refresh_links()` 里原本有一句：

```c
s_eco.alert_active = false;    /* P1 接入阈值判定后改写 */
```

它被 `mqtt_task` **每 10 秒**调一次（还有网络事件回调）。于是任何由采样算出的告警
**活不过 10 秒**就被清掉 —— 现象会非常迷惑："告警偶尔闪一下就没了，像是随机的"。
该行已删除，现在 `alert_mask` / `alert_active` **只有一个写者**：阈值计算处。

> 这一条是并行复核（Plan 子智能体）发现的，不在我原本的设计视野里。
> **值得记住**：新增一个"周期性写共享状态"的任务时，要先找出**所有**写者。

## 7. 方法论

本轮基本没走弯路，值得记的是**为什么**：

1. **引脚表是实测校准过的** —— 前几轮把 pinmap 钉牢的回报，这次一次探测成功。
2. **字节序有双重印证** —— 驱动源码（`swap_data=0`）+ 参考实现（同样 `bswap16`）
   + 本次 LCD 侧刚踩过的同源坑。三条独立证据指向同一结论。
3. **并发危害提前写在设计里** —— "拍照不能在锁内"是设计时就想清楚的，
   不是出问题后补的。上板验证时专门测了"拍摄期间界面是否正常"。
4. **并行复核换来了一个自己看不见的 bug** —— `alert_active` 被周期性清零。
   复核者读的是"所有写这个状态的地方"，而我只盯着"我要写的地方"。
5. **仍然犯了一次"想当然"** —— 全程按 OV2640 写注释，直到串口打出 GC0308。
   这是本项目第四次同类问题（1 比特字段错位、C1 引脚冲突、背光极性、现在的型号）。

> **通用规则**：凡是"型号 / 参数 / 极性 / 顺序"这类**可以一查就准**的事实，
> 在上板之前应当标注为"待实测"，而不是写成肯定句。写肯定句的成本很低，
> 但它会误导所有后来读它的人 —— 包括未来的自己。
